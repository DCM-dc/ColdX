## Product requirements carried forward

The source conversation explicitly established these requirements:

1. Let users act through clicks, direct manipulation, and small edits. Their attention should stay on the effect they want.
2. Prepare a useful default from the available evidence. Show the result or preview before lengthy explanation; expose details on demand.
3. Generate whatever interaction the task needs. Cards and single-choice questions are useful controls, not the boundary of possible interfaces.
4. A meaningful submission returns actual values to the original DSH task and execution continues. Local preview clicks should respond immediately without requesting another model completion.
5. Continue autonomously when no human decision is needed. Discover, author, test, and activate a native plugin when it supplies a missing capability.
6. Refine native components as well as ColdX components: sidebar, composer, messages, tools, settings, menus, and dialogs.
7. Apply a coherent iOS 18-inspired motion language: immediate response, interruptible transitions, natural settling, readable states, keyboard and reduced-motion support.

Later corrections in the receiving task remain authoritative: retain the neutral visual structure; use frosted materials rather than a highly transparent or liquid-glass redesign; keep the removed sample/experience feature disabled.

Latest priority: generated interfaces belong inside the chronological conversation, at the same content level as other messages. They must not occupy a separate dock between the transcript and composer, hide the transcript, or override native bottom-follow behavior. This supersedes the earlier main-stage/page-history presentation.

The client now registers `coldx_present_page` and `coldx_interact` at native `tool.call.toolview` positions. It matches the full call ID, retains iframe identity across call completion, uses measured content height in normal flow, and leaves ordering/scrolling to DSH. Ordinary questions, approvals and plan reviews keep native handling. See the latest section of `docs/verification.md` for evidence and the remaining browser-verification blocker.

## Current implementation and evidence boundaries

- Native interaction tools, sandboxed generated pages, authenticated answer delivery, page history, and completion-state projection are present.
- Source-task reports of 97 passing tests, live color-selection delivery, and 12 verified sample files are historical evidence. The sample feature was subsequently disabled at the user's request.
- The receiving task added spring/motion and frosted-material refinements, iframe readiness handling, and a stream compatibility guard for leaked DSML/control text.
- Protocol normalization is an execution fix. It does not prove that a model chooses a useful interface autonomously.
- The newly added tool activity projection represents the current turn. It must not be described as persistent multi-turn history.
- Automatically promoting any tool activity to a primary “execution” page conflicts with the approved effect-first design and creates extra pages even for a short answer using `coldx_finish`. Remove that automatic promotion; preserve access to the native process view.
- A running process on port 3086 does not prove it has loaded the latest host module or browser bundle. Verify the served version and current behavior before claiming a fix is live.
